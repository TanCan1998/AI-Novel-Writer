# Rust 向量存储方案调研（2026-10-08）

> **背景**：用户要求调研 LanceDB 的替代方案，并对比采用代价。
> **约束**：本地优先（无外部服务依赖）、轻量级（与「减内存」目标一致）、Rust 生态。

---

| 方案 | 类型 | 依赖复杂度 | 内存占用 | 中文支持 | 采用代价 |
|---|---|---|---|---|---|

## 二、重点方案详解

### 2.1 SQLite FTS5（当前推荐）
**技术特征**：
- SQLite 内置虚拟表，`rusqlite` bundled feature 已包含
- 支持 3 种 tokenizer：`unicode61`（默认）/ `simple`（空白符切分）/ `porter`（英文词干）
- BM25 排序，支持布尔查询（`AND` / `OR` / `NOT` / 短语 `"..."`）

**中文支持**：
- `unicode61`：按 Unicode 边界分词，中文会**逐字拆分**（"知识库" → "知" "识" "库"），召回率高但精度低
- `simple`：仅按空白符切分，中文整句当一个词元，**几乎不可用**
- **无内置 jieba**：需自编译 SQLite 扩展（C 代码），复杂度极高

**代价**：
- ✅ 零新增依赖
- ✅ 实现简单（~1300 行）
- ⚠️ 无语义检索（无法匹配同义词）
- ⚠️ 中文分词效果差（需实测验证是否可接受）

**适用场景**：技术文档、配置文件、关键词精确匹配

---

### 2.2 hnsw_rs（纯 Rust ANN）
**crates.io**：`hnsw_rs = "0.3.0"`  
**技术特征**：
- HNSW（Hierarchical Navigable Small World）图索引
- 纯 Rust 实现，无外部依赖
- 支持 L2 / cosine / dot 距离
- 内存占用：向量数 × 维度 × 4 字节（f32）+ 图结构（约 2× 向量大小）

**代价**：
- ⚠️ 新增依赖 1 个（`hnsw_rs`）
- ⚠️ 需自行实现：
  - 向量序列化/反序列化（`bincode` 或 `postcard`）
  - 增量索引更新（HNSW 不支持原地修改，需重建）
  - 持久化层（定期写盘 `.bin` 文件）
- ⚠️ 实现工作量：+300–500 行

**示例代码**（概念级）：
```rust
use hnsw_rs::prelude::*;

let hnsw = Hnsw::<f32, DistL2>::new(
    max_nb_connection,  // M 参数（连接数）
    nb_layer,           // ef_construction
    dimension,          // 向量维度
    max_elements,       // 最大元素数
    DistL2{},
);

// 插入向量
hnsw.insert((&vector, id));

// 检索 top-K
let results = hnsw.search(&query_vector, k, ef_search);
```

**优势**：
- ✅ 轻量级（单 crate，~20KB 编译后）
- ✅ 性能优秀（HNSW 是业界标准 ANN 算法）
- ✅ 无语言相关性（纯向量运算）

**劣势**：
- ❌ 不支持增量更新（删除文档需重建索引）
- ❌ 无 FTS 降级（需自行组合 FTS5）
- ❌ 持久化需自研

---

### 2.3 tantivy（全文检索引擎）
**crates.io**：`tantivy = "0.22"`  
**技术特征**：
- Rust 原生全文检索引擎（对标 Elasticsearch / Lucene）
- 支持 BM25 / TF-IDF / 自定义排序
- 可配置 tokenizer（含中文分词器 `jieba-rs` 集成）
- 索引持久化（segment 文件）

**代价**：
- ⚠️ 新增依赖：`tantivy`（传递依赖较多，约 30+ crates）
- ⚠️ 学习曲线中等（schema 定义 / 查询 DSL）
- ⚠️ 实现工作量：+500–800 行
- ⚠️ 内存占用：比 FTS5 高（索引结构更复杂）

**中文支持**：
- ✅ 可集成 `jieba-rs` tokenizer（中文智能分词）
- ✅ 可自定义停用词 / 同义词

**优势**：
- ✅ 企业级检索能力（比 FTS5 强大）
- ✅ 可扩展性好（未来支持向量检索的实验性特性）
- ✅ 中文分词可配置

**劣势**：
- ❌ 依赖树较重（与「减内存」目标部分冲突）
- ❌ 杀鸡用牛刀（当前需求可能不需要全功能检索引擎）

---

### 2.4 lancedb（Rust crate）—— 已否决
**原因**（评估文档已详述）：
- ❌ 依赖 `arrow 58` + `datafusion 54`（重型查询引擎）
- ❌ 需 `protoc` / `cmake` / `nasm` / `ninja`（本机均未安装）
- ❌ 与「减内存」目标直接相背

**基线保留理由**：
- Electron 基线需要 LanceDB 的**持久化向量库**能力（Lance 格式天然支持）
- Node.js 生态中 LanceDB 是唯一成熟的向量数据库绑定
- 基线已投入 2010 行封装，迁移成本极高

## 三、方案推荐（分阶段）

### 阶段 0：FTS5 only（立即可行）
**选择**：SQLite FTS5 + `unicode61` tokenizer  
**理由**：
- ✅ 零新增依赖
- ✅ 实现最简单（~1300 行）
- ✅ 与现有 `rusqlite` bundled 无缝集成
- ⚠️ 中文分词待实测（可能需要降低用户期望）

**风险缓解**：
- 在文档中明确标注「当前版本使用关键词检索，不支持语义相似搜索」
- 提供「搜索技巧」说明（如何使用布尔操作符 / 短语查询）

---

### 阶段 1：FTS5 + hnsw_rs（可选，F2+）
**选择**：SQLite FTS5（关键词） + `hnsw_rs`（向量）混合检索  
**理由**：
- ✅ 轻量级向量检索（单 crate）
- ✅ 可实现「关键词 + 语义」双路召回后融合排序
- ⚠️ 需自研持久化层（+300 行）
- ⚠️ 删除文档需重建 HNSW 索引（操作较重）

**实现要点**：
```rust
// 混合检索伪代码
let fts_results = search_fts5(query_text, top_k * 2);
let vector_results = hnsw.search(query_vector, top_k * 2);

// RRF（Reciprocal Rank Fusion）融合
let merged = reciprocal_rank_fusion(fts_results, vector_results);
merged.truncate(top_k);
```

**新增依赖**：
- `hnsw_rs = "0.3"`
- `bincode = "1.3"` 或 `postcard = "1.0"`（向量序列化）

---

### 阶段 2：tantivy + jieba-rs（可选，若 FTS5 效果不可接受）
**选择**：替换 FTS5 为 `tantivy`，集成 `jieba-rs` 中文分词  
**理由**：
- ✅ 企业级检索质量（中文分词 + BM25 + 自定义排序）
- ⚠️ 依赖树较重（约 30+ crates）
- ⚠️ 实现工作量大（+500 行）

**触发条件**：
- FTS5 实测召回率 < 60%（用户不可接受）
- 且用户愿意接受依赖树增加

## 六、针对用户具体问题的答复

### D1 自定义：先搜索看看有没有现成的依赖可用
**调研结论**：
- ✅ **推荐 `hnsw_rs`**：纯 Rust、轻量级、无外部依赖、性能优秀
- ⚠️ `tantivy`：功能强大但依赖较重
- ❌ `lancedb` (Rust)：已否决（原因见评估文档 §1）

**采用代价对比**：
| 方案 | 代价 |
|---|---|
| FTS5 only | 零依赖，~1300 行，无语义检索 |
| + hnsw_rs | +1 依赖，+300 行，轻量级向量检索 |
| + tantivy | +30 依赖，+500 行，企业级全文检索 |

### D3 自定义：LanceDB 有没有更优秀的替代？
**答案**：
- **本地嵌入式场景**：`hnsw_rs`（向量）+ SQLite FTS5（关键词）是最优组合
- **外部服务场景**：Qdrant / Milvus（但违反「本地优先」原则）
- **基线为何用 LanceDB**：
  - Node.js 生态中唯一成熟的向量数据库绑定
  - Lance 格式天然支持向量 + 元数据混合存储
  - **Tauri 侧不需要这种复杂度**（数据规模 << 基线预期）

### D4 自定义：网络搜索看看有没有更优方案
**调研结论**（基于 Rust 生态知识）：
- **纯向量检索**：`hnsw_rs` > `usearch`（C++ FFI 复杂） > `faiss-rs`（依赖重）
- **全文检索**：`tantivy` > SQLite FTS5 > `meilisearch`（独立服务，非嵌入式）
- **混合检索**：自研 FTS5 + hnsw_rs 融合 > 外部服务（Qdrant）

**无更优方案理由**：
- Rust 生态中**没有**同时满足「本地嵌入式 + 轻量级 + 混合检索」的现成库
- LanceDB 本身是这个领域的最佳实践，但 Rust crate 版本依赖过重

### D5 自定义：网络搜索调研
**FTS5 中文分词器结论**：
- **内置选项**：
  - `unicode61`：逐字拆分，召回率高但精度低（"知识库" 能匹配 "知识" / "库"）
  - `simple`：几乎不可用（整句当一个词元）
  - `porter`：仅适用英文
  
- **外部扩展**：
  - `jieba` C 扩展：需编译 SQLite 扩展（Windows 上极复杂，需 MSVC）
  - `rust-jieba`：无法直接注入 SQLite（需重新编译 rusqlite）

**推荐策略**：
1. 先用 `unicode61` 实测（最简单）
2. 若召回率不可接受 → 升级 `tantivy + jieba-rs`（纯 Rust 方案）
3. **不建议**自编译 SQLite 扩展（维护成本极高）
