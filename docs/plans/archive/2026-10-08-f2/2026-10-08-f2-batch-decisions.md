### D1：是否采纳「FTS only」阶段 0？
**用户答复**：自定义 —— 先搜索看看有没有现成的依赖可用，对比采用的代价

**调研结果**（见 `vector-alternatives-survey.md` §2）：
| 方案 | 新增依赖 | 实现行数 | 内存增量 | 中文效果 | 代价评级 |
|---|---|---|---|---|---|
| **FTS5 only** | 0 | ~1300 | 0 | ⭐⭐⭐ | 最低 |
| **FTS5 + hnsw_rs** | 2 (`hnsw_rs`, `bincode`) | ~1600 | +5–10 MB | ⭐⭐⭐⭐ | 中 |
| **tantivy + jieba-rs** | 30+ | ~1800 | +10–20 MB | ⭐⭐⭐⭐⭐ | 高 |

**最终决策**：
- ✅ **采纳阶段 0（FTS5 only）** 作为 F2 批次目标
- ⚠️ **预留升级路径**：前端接口保留 `queryVector` 参数（当前忽略），未来可无缝升级至阶段 1

**理由**：
- 零新增依赖，符合「快速交付」原则
- 调研未发现显著更优的轻量级方案
- `hnsw_rs` 是最佳向量候选，但需 F2 开工前**实测 FTS5 中文效果**后再决定是否引入

### D2：是否删除多模型空间逻辑？
**用户答复**：否 —— 代价是需迁移基线 600 行 embedding space 管理逻辑，复杂度高

**含义解读**：
- ❌ **不删除**多模型空间逻辑
- ✅ **需迁移**基线 `electron/vector-store.ts` 的 embedding space 注册表机制

**后果**：
- **工作量增加**：从 ~1300 行（单空间简化版）→ ~1900 行（含多 generation 管理）
- **复杂度增加**：需实现 `embedding-spaces.json` 读写 / active generation 切换 / 重建计划
- **内存占用**：保留多个历史向量表（inactive generation）会增加存储

**实施要求**（F2 批次内）：
1. 迁移 `EmbeddingSpaceRegistry` 结构体及序列化逻辑
2. 实现 `planEmbeddingRebuild()` / `activatePlannedEmbeddingSpace()` / `rebuildPlannedEmbeddingSpace()`
3. 支持多 generation 表并存（`generation_1.lance` / `generation_2.lance` 风格命名）
4. 实现 `getEmbeddingSpaces()` 查询接口（前端显示多模型历史）

**风险**：
- ⚠️ 与「减内存」目标部分冲突（多向量表会占用额外空间）
- ⚠️ 实现复杂度高，可能导致 F2 工期延长 50%+

### D3：是否强制改名向量目录为 `lorekeeper-vectors/`？
**用户答复**：自定义 —— LanceDB 有没有更优秀的替代？

**调研结果**（见 `vector-alternatives-survey.md` §6）：
- **本地嵌入式场景**：`hnsw_rs`（向量）+ SQLite FTS5（关键词）是最优组合
- **外部服务场景**：Qdrant / Milvus（违反「本地优先」原则）
- **基线保留 LanceDB 的理由**：Node.js 生态唯一成熟方案 + Lance 格式优势

**结论**：
- ✅ **Tauri 侧不使用 LanceDB**（原因：依赖 arrow 58 + datafusion 54，与「减内存」相背）
- ✅ **替代方案**：
  - 阶段 0：SQLite FTS5（纯关键词）
  - 阶段 1：SQLite FTS5 + `hnsw_rs`（混合检索）
  - 阶段 2：`tantivy` + `jieba-rs`（若 FTS5 效果不可接受）

**路径改名决策**（回到 D3 原问题）：
- ✅ **强制改名**为 `.vela/lorekeeper-vectors/`（隔离红线，不可妥协）
- ✅ 同时改名 `.vela/lorekeeper-embedding-spaces.json`
- ❌ **不提供**旧数据迁移脚本（双栈隔离前提，Tauri 侧空启动）

**实施清单**（6 处常量修改）：
```rust
// tauri-app/src-tauri/src/vector_store/paths.rs
const VECTOR_DIR_NAME: &str = "lorekeeper-vectors";
const EMBEDDING_REGISTRY_FILE: &str = "lorekeeper-embedding-spaces.json";

fn vector_db_path(project_path: &Path) -> PathBuf {
    project_path.join(".vela").join(VECTOR_DIR_NAME)
}

fn registry_path(project_path: &Path) -> PathBuf {
    project_path.join(".vela").join(EMBEDDING_REGISTRY_FILE)
}
```

### D4：是否需要阶段 1（Rust 向量存储 + 混合检索）？
**用户答复**：自定义 —— 网络搜索看看有没有更优方案

**调研结果**（见 `vector-alternatives-survey.md` §6）：
- **纯向量检索**：`hnsw_rs` > `usearch`（C++ FFI 复杂） > `faiss-rs`（依赖重）
- **全文检索**：`tantivy` > SQLite FTS5 > `meilisearch`（独立服务）
- **混合检索**：自研 FTS5 + hnsw_rs 融合 > 外部服务（Qdrant）

**最终决策**：
- ⚠️ **F2 批次内暂不实现**阶段 1
- ✅ **前置条件**：F2 开工前执行 **1 天 FTS5 中文实测**（见下方 §实测计划）
- ✅ **实测通过标准**：召回率 ≥ 60% 且用户可接受 → 阶段 0 交付，阶段 1 押后至 F2+
- ⚠️ **实测不通过**：召回率 < 60% → F2 批次内必须实现阶段 1（`hnsw_rs`）或阶段 2（`tantivy`）

**阶段 1 技术栈（若启用）**：
- `hnsw_rs = "0.3"`
- `bincode = "1.3"` 或 `postcard = "1.0"`
- 实现工作量：+300–500 行
- 新增文件：`src/vector_store/ann.rs` / `src/vector_store/hybrid.rs`

### D5：FTS5 中文分词器选择？
**用户答复**：自定义 —— 网络搜索调研

**调研结果**（见 `vector-alternatives-survey.md` §6）：
| 分词器 | 效果 | 复杂度 | 推荐度 |
|---|---|---|---|
| `unicode61`（默认） | 逐字拆分，召回高精度低 | 零配置 | ⭐⭐⭐⭐ |
| `simple` | 整句当一个词元 | 零配置 | ❌ 不可用 |
| `porter` | 仅适用英文 | 零配置 | ❌ 不可用 |
| `jieba` C 扩展 | 优秀 | 极高（需编译 SQLite） | ❌ 不推荐 |
| `tantivy + jieba-rs` | 优秀 | 高（+30 依赖） | ⭐⭐⭐（备选） |

**最终决策**：
- ✅ **F2 阶段 0 使用 `unicode61`**（默认，零配置）
- ⚠️ **实测后决定**：若召回率不可接受 → 升级至 `tantivy + jieba-rs`（阶段 2）

### 评估指标
| 指标 | 计算方式 | 通过标准 |
|---|---|---|
| **召回率** | 相关文档被检索到的比例 | ≥ 60% |
| **精度** | 检索结果中相关文档的比例 | ≥ 40% |
| **查询延迟** | 单次查询平均耗时 | < 50ms |
| **内存占用** | 索引大小 / 语料大小 | < 1.5× |

### 对比基准
| 方案 | 召回率 | 精度 | 延迟 | 备注 |
|---|---|---|---|---|
| FTS5 `unicode61` | ? | ? | ? | **待测** |
| FTS5 `simple` | ? | ? | ? | 预期不可用 |
| 基线 LanceDB（理论值） | ~85% | ~70% | ~30ms | 语义检索上限 |

### 实测步骤
1. **环境搭建**（1h）：
   - 在 `tauri-app/src-tauri/` 新建 `examples/fts_benchmark.rs`
   - 用 `rusqlite` 创建 FTS5 虚拟表
   - 导入测试语料（~1000 条小说章节片段）

2. **查询测试**（2h）：
   - 执行 15 个测试用例
   - 记录每个查询的召回率 / 精度 / 延迟
   - 对比 `unicode61` vs `simple`

3. **结果分析**（1h）：
   - 计算平均召回率 / 精度
   - 识别失败的典型场景（如同义词 / 长尾查询）
   - 输出实测报告（Markdown 表格 + 结论）

4. **决策输出**（30min）：
   - 若召回率 ≥ 60% → 阶段 0 可行，F2 批次只做 FTS5
   - 若召回率 < 60% → F2 批次内必须引入 `hnsw_rs` 或 `tantivy`

**预期完成时间**：1 个工作日（含环境搭建 + 测试执行 + 报告撰写）
